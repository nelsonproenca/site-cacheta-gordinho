## Deploy (Vercel)

Standard Next.js App Router project — Vercel auto-detects the framework, runs `npm run build`, and needs no `vercel.json`. Node `>=20.9.0` is pinned in `package.json`'s `engines` (Next 16's own peer requirement) so a project-level Node version override on Vercel picks something compatible.

- **Env vars** (Vercel project → Settings → Environment Variables): the four in `.env.local.example` — `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (server-only, never expose to a `NEXT_PUBLIC_*` var or client bundle), `NEXT_PUBLIC_SITE_URL`. Set `NEXT_PUBLIC_SITE_URL` to the real production domain, **not** `http://localhost:3000` — it's the only thing `metadataBase` (`app/layout.tsx`) and the magic-link/signup email redirect (`lib/actions/auth.ts` → `${NEXT_PUBLIC_SITE_URL}/auth/confirm`) have to go on.
- **Supabase Auth → URL Configuration**: add the production `NEXT_PUBLIC_SITE_URL` (and its `/auth/confirm` path) to the project's allowed Redirect URLs in the Supabase dashboard — this is external config, not something a code change here can do. Without it, admin login magic links/signup confirmations will redirect to a rejected URL.
- **Migrations are not part of the build.** `supabase db push` is a separate, manual step (see Commands above) — deploying a commit that assumes a new migration is applied does nothing to actually apply it. Push pending migrations (and regenerate `lib/supabase/database.types.ts`) before or alongside deploying code that depends on them, not after.
- **Storybook is not part of `npm run build`** — Vercel's default build only runs the Next.js app, so its dependencies/config don't affect the deployed site. If you also want Storybook hosted (e.g. a separate `storybook.<domain>` project), that's a second Vercel project pointed at this same repo with build command `npm run build-storybook` and output directory `storybook-static`.

## What this project is

A platform to manage a TikTok creator's live "Caxeta" (card game) streams: manual scoring of matches per live session, weekly/season rankings, a Saturday "Caxetão" event with configurable registration (principal/substitute slots, closing by time or by count), World-Cup-style championships (groups → knockout), and multi-account management (one platform, several managed TikTok accounts, admins/moderators scoped per account).

Full domain rules, entities, and the proposed Postgres schema are in `prd.md` §4–§7 — do not re-derive these from scratch, reference them.

## Key architectural constraints (non-obvious, drives everything)

- **No TikTok API access for live/follower data.** There is no official API to read live-room participants or a creator's follower list. All match results are entered manually by an admin/moderator through the panel during/after the live. "Active/most engaged followers" are computed from in-platform activity (matches played, live participations, Caxetão/championship participation) — never fetched from TikTok. See `prd.md` §1.1.
- **Players are global, participation is per-account.** A `players` row is one person across the whole platform; their scores, live participations, Caxetão registrations, and championship history are always scoped to a `tiktok_account_id`. Any query/feature touching scores or rankings must filter by the active managed account.
- **Players have no password-based auth** (lightweight signup: display name + unique TikTok handle, optional WhatsApp). Only admins/moderators authenticate (Supabase Auth). Don't build a full auth flow for players in the MVP.
- **Scoring rules are per-account and admin-configurable**, not hardcoded constants — points for each result type (e.g. "vitória lambreta", "derrota normal") live in a `scoring_rules` table and are editable without a code change. `match_results.points_awarded` is a snapshot at write time, so historical totals must never be recalculated from current `scoring_rules` values.
- **Multi-tenancy by TikTok account**: an admin can own/moderate several `tiktok_accounts`; access is governed by `admin_account_access` (role: owner/moderator per account). Authorization (Supabase RLS) should key off this join table, not off a single global admin role.

## Fase 1 (MVP) — implemented

Migrations `supabase/migrations/2026071500000{1..11}_*.sql` create `admins` (1:1 with `auth.users`), `tiktok_accounts`, `admin_account_access`, `players`, `scoring_rules`, `score_periods`, `live_sessions`, `live_participants`, `matches` (with `tiktok_account_id` denormalized — deliberate deviation from prd.md §7 to keep every write policy a single `has_account_access()` check instead of a join), and `match_results`. Two SECURITY DEFINER helper functions (`has_account_access`, `is_account_owner`) back nearly every RLS policy — reuse them rather than re-writing the `admin_account_access` exists-subquery. Accounts are created exclusively through the `create_tiktok_account` RPC (also seeds the 4 default `scoring_rules`), because `tiktok_accounts` has no direct insert policy — the first `admin_account_access` row for a new account can't otherwise satisfy `is_account_owner()`.

Later migrations (`2026071700001{3,4}_*.sql`): `score_periods` gained an open/closed `status` (unique partial index caps it at one open period per account) and `live_sessions`/`matches` gained a denormalized `score_period_id`, copied from the live session onto every match via a `BEFORE INSERT` trigger — mirrors the `tiktok_account_id` denormalization so a period's ranking is a single-level join (`lib/scoring/get-ranking.ts` → `getPeriodRanking`). **Gotcha this created and fixed**: any table that denormalizes `tiktok_account_id` (or similar) purely for RLS speed is a spoofing risk — `has_account_access(tiktok_account_id)` only validates the column value on the row being written, not that it actually agrees with a related row's real account (e.g. `matches.live_session_id` could point at a different account's live session while `tiktok_account_id` still names an account the caller owns). `matches` now has a second trigger (`matches_validate_account`) that raises if the two disagree — replicate that pattern for any future denormalized-account-id table instead of trusting RLS alone. Admin UI for all this lives at `/admin/[accountId]/ranking` (current period + podium + close action) and `/admin/[accountId]/ranking/[periodId]` (historical periods); periods are created manually by the admin (label typed by them), never auto-opened.

`players` has no insert/update policy for anon or authenticated at all — both public self-registration and admin "quick add" during a live go through Server Actions using `lib/supabase/service.ts` (service-role, bypasses RLS), so handle normalization/dedupe lives in one place. Every other admin-facing write goes through the regular per-request client (`lib/supabase/server.ts`) and relies on RLS, not application-level role checks.

Admin routes live under `app/admin/(shell)/` (route group, doesn't affect the URL) so `app/admin/login` can render without the sidenav shell that the rest of `/admin/**` gets from `app/admin/(shell)/layout.tsx`. `proxy.ts` redirects unauthenticated requests to `/admin/login` for anything under `/admin` except that route.

Self-signup (the "Criar conta" mode on the login form) used to grant full admin capability the moment the email was confirmed — any visitor could sign up and immediately call `create_tiktok_account()`. Migration `20260718000018_admins_approval.sql` adds `admins.status` (`pending` by default for new signups, existing rows backfilled `approved`); `lib/supabase/middleware.ts` (`proxy.ts`) redirects any authenticated-but-not-approved admin to `/admin/aguardando` for everything under `/admin` except that page and `/admin/login`, and `create_tiktok_account` itself re-checks `is_approved_admin()` as defense in depth (same reasoning as `matches_validate_account` — don't trust a single layer). An existing approved admin reviews the queue at `/admin/solicitacoes` (`lib/actions/admin-approvals.ts`): "Aprovar" is a plain RLS-gated update (`admins_approve_pending` policy, pending → approved only) on the regular per-request client; "Excluir" needs the service-role client instead, since deleting the underlying `auth.users` row (which cascades to `admins`) isn't something any RLS policy can grant — the caller's own approved status is checked explicitly there for the same reason `adminRegisterPlayer` checks it (service role bypasses RLS entirely). **Gotcha this created and fixed**: an UPDATE policy's `with check` isn't the only thing that can reject a status-changing write — Postgres also re-validates the *mutated* row against the table's SELECT policies whenever the caller might get that row back (which PostgREST's `.update()` does even without an explicit `.select()`), and fails with the exact same "new row violates row-level security policy" error either way. A SELECT policy scoped to `status = 'pending'` let the approve `UPDATE` find the row but then couldn't see it anymore once its status flipped to `'approved'`; the fix was broadening `admins_select_all_for_approved` to cover every row, not just pending ones. `tests/rls.test.ts` and `scripts/smoke-test.ts` both fast-forward their throwaway admins to `'approved'` right after creating them — they test tenant isolation, not this gate.

`lib/scoring/get-ranking.ts` is the single source of truth for ranking math (points desc → count of positive-point results desc → handle alphabetical). The exact "vitórias lambreta"-specific tie-break from prd.md §12 is still an open decision (scoring_rules has no category column to distinguish a lambreta win from a normal one) — don't invent a category column without checking that decision first.

## Fase 2 (Caxetão) — implemented

Migrations `supabase/migrations/2026071700001{5,6,7}_*.sql` add `caxetao_events` and `caxetao_registrations`, then extend `matches` with a `caxetao_event_id` column so a match can belong to either a live session or a Caxetão event (`matches_exactly_one_source` check constraint), extending `matches_validate_account`/`matches_set_score_period` accordingly — Caxetão matches deliberately get no `score_period_id`, since Caxetão is a separate competition from the weekly/season ranking. `caxetao_registrations` has no insert policy for anon/authenticated at all (same reasoning as `players`): both self-registration and admin manual add funnel through `registerPlayerForEvent` (`lib/caxetao.ts`) on the service-role client, which is the one place that assigns principal-vs-substitute and FIFO `queue_position`. Status *updates* after creation (presence, cancellation, promotion) go through the regular per-request client instead, since admin already has direct RLS write access there and there's no cross-row math to protect.

`lib/caxetao.ts` also has `syncCaxetaoEventStatus` — lazily flips `scheduled → registrations_open → registrations_closed` against the wall clock (same "no cron in this stack" pattern as `closeStaleLiveSessions`), called wherever a single event is read before acting on it. **Gotcha this created and fixed**: `registerPlayerForEvent` originally closed the event (`status = 'registrations_closed'`) as soon as `max_principals` was reached — but prd.md §4.5 says players beyond that cap should keep signing up as substitutes (up to `max_substitutes`), so reaching the principal cap must *not* stop registration outright. It now only auto-closes once principals **and** substitutes are both at capacity; an event with an uncapped substitute queue (`max_substitutes` null) is therefore never auto-closed by count, only by the time deadline or an admin. The three pt-BR label maps (`CAXETAO_STATUS_LABEL`, `CAXETAO_STATUS_VARIANT`, `CAXETAO_CLOSE_RULE_LABEL`) live in this same file — every page that renders an event's status/close_rule imports them rather than redefining its own copy.

The admin "Novo Caxetão" form (`create-event-form.tsx`) only offers `close_rule` **time** or **count** as a two-button toggle (no default selected, submit disabled until one is picked) — `both` is still a valid DB value and still handled by `createCaxetaoEvent`/`registerPlayerForEvent`, it's just not reachable from this form; a deliberate scope-simplification, not a bug, if you're wondering why the UI only shows two options where the schema allows three. The two field groups (time window vs. capacity) are mutually exclusive and always render on their own row, never mixed with `Data do evento`/`Regra de encerramento`. Picking "Por quantidade" submits `registration_opens_at` as "now" (São Paulo wall time, via `nowInSaoPauloAsDatetimeLocal`) through a hidden input instead of asking the admin to schedule an opening — that mode has no deadline for an opening time to be scheduled against.

Admin UI lives at `/admin/[accountId]/caxetao` (list + create) and `/admin/[accountId]/caxetao/[eventId]` (principals/substitutes, manual add via modal, cancel/no-show, FIFO promotion, `Iniciar evento`/`Finalizar evento` stage transitions). Both the list and detail cards follow a title/subtitle/plain-text hierarchy: `Data · Regra` in `font-display` as the title, rule-specific values as an `.text-ink-dim` subtitle, and — only while registration is open — a third plain-text line with either a live countdown (`components/closing-countdown.tsx`, `ClosingCountdown`) or "Faltam N jogadores para encerrar as inscrições".

**Player view (public, no auth)**: `app/(public)/[accountHandle]/layout.tsx` wraps `ranking`/`caxetao`/`inscricao` in a shared tab nav (`components/ui/tab-bar.tsx` — also used by the admin account shell, see below). `/[accountHandle]/caxetao` shows the same principals/substitutes lists as admin, a `.card-stat`-styled (big number) countdown-or-remaining-slots readout for extra visibility, and self-registration via a modal (`caxetao-register-modal.tsx`) instead of an inline form. `RankingBoard` (`components/ranking-board.tsx`, shared by admin and public ranking pages) got a search box that filters by name/@handle while still showing each match's real rank, not its index in the filtered list. The root `/` page is the player entry point — it lists active `tiktok_accounts` linking into their `/ranking`, with `/admin/login` demoted to a small link at the bottom instead of being the page's main call to action.

`components/ui/modal.tsx` is a `<dialog>`-backed modal shared by every "open a form in a modal" flow (`register-player-modal.tsx`, `caxetao-register-modal.tsx`) — it renders the `<dialog>` itself as an invisible full-viewport flex-centering frame with the visible card as a nested `.modal-content` div. **Gotcha this created and fixed**: don't center a `<dialog>` by relying on the UA stylesheet's `dialog:modal { margin: auto }` — Tailwind v4's Preflight resets `margin: 0` in `@layer base`, and even though that's a *lower*-priority layer than unlayered author CSS, it's still higher priority than the UA stylesheet's own (lowest) tier, so Preflight's reset silently wins and the dialog collapses to the top-left corner. Center with flex (`.modal-overlay[open]{ display:flex; align-items:center; justify-content:center; }`) instead — it has no dependency on margin at all. `ModalHeader` (title + close-✕ button) is exported from the same file since it was identical boilerplate at every modal call site.

**Known gap**: `tests/rls.test.ts` does not yet cover `caxetao_events`/`caxetao_registrations` — deferred to the end of the phase per explicit instruction rather than extended after each migration (unlike the stated convention above). Extend it before starting Fase 3.

## Super admin & account deletion (implemented)

Migration `20260724000020_super_admin.sql` adds `admins.is_super_admin` (boolean, default false) and redefines `has_account_access`/`is_account_owner` (`20260715000003_admin_account_access.sql`) to `... or is_super_admin()` — gives a super admin automatic access to every one of the ~14 tables those two functions already gate. This is a deliberate override of this file's own earlier note ("authorization should key off `admin_account_access`, not a single global admin role") — the user explicitly asked for someone who can manage every account and every admin at once. `revoke update (is_super_admin) on admins from authenticated, anon` stops an already-approved admin from self-escalating via `.update({status:'approved', is_super_admin:true})` through `admins_approve_pending`'s loose `with check` (which only pinned `status`) — RLS row policies can't express "this column is off-limits regardless of the row predicate," only a column-level revoke does. The first super admin was seeded directly: `update admins set is_super_admin = true where email = 'nelsonhaproenca@gmail.com'`.

Account deletion (`delete_tiktok_account` RPC, `20260724000021`) mirrors `create_tiktok_account`: `tiktok_accounts` has no direct delete policy, only this `security definer` RPC, gated by `is_account_owner` and requiring the caller to re-type the account's `@handle` as confirmation (`app/admin/(shell)/contas/delete-account-modal.tsx`) — given the blast radius (wipes the account's entire ranking, lives, results, and Caxetão history). **Gotcha fixed in `20260724000022`**: `match_results.scoring_rule_id` and `match_result_edits.*_scoring_rule_id` have no `on delete cascade` to `scoring_rules` (by design — see `20260715000011_match_results.sql`), so the cascade from `tiktok_accounts` reached `scoring_rules` before those two tables were empty and the FK check fired mid-cascade. The RPC now deletes `match_result_edits`/`match_results` scoped to the account explicitly before the delete that cascades through the rest — same fix already used in `scripts/smoke-test.ts`'s `cleanup()`.

## User roles: Streamer, Moderador, Super Admin (implemented)

Migration `20260724000024_admin_user_type.sql` adds `admins.user_type` (`'streamer'|'moderador'`, nullable — a super admin doesn't need one) and `admins.streamer_id` (self-FK, `on delete set null`, only set for moderadores). **This is orthogonal to `admin_account_access.role`** (`'owner'|'moderator'`, English, per-account — untouched) — the two similar-looking values (`moderator` vs `moderador`) name different things on purpose: one is an access level on one account, the other is the category of person. A streamer can still own several accounts (this did not become a 1:1 relationship). Signup (`app/admin/login/login-form.tsx`, "Criar conta" mode) now picks the type and, for moderadores, which streamer to link to — the streamer list comes from `app/admin/login/page.tsx` via `createServiceClient()`, since that page renders pre-session and `admins` has no public select policy. Trigger `admins_validate_streamer` rejects a `streamer_id` that doesn't point at a real `user_type='streamer'` row.

Approving an admin now goes through the RPC `approve_pending_admin` instead of the old direct `update({status:'approved'})` — the `admins_approve_pending` policy was **removed**, this RPC is the only path now (same "no direct write policy, only via RPC" pattern as `create_tiktok_account`). Approving a moderador auto-copies the same `admin_account_access` rows (`role='moderator'`) their linked streamer already has — that's how "same access as the streamer" is satisfied without waiting on a manual `AddModeratorForm` afterward. It's only a snapshot at approval time though: if the streamer gains a new account later, the moderador isn't synced automatically — that still needs the existing manual flow (`lib/actions/accounts.ts`'s `addModerator`) for that specific account.

## Partidas: pairing 2 players within one account (implemented)

`matches` gained `player_a_id`/`player_b_id` (nullable, `20260724000023_matches_player_pairing.sql`) to hold a real 2-player pairing on a single `matches` row — until then every `matches` row was created with **one** player only (`recordMatchResult`, `lib/actions/lives.ts`), never two. `match_results` is untouched (still `not null`), so a freshly-created pairing with no result yet needs somewhere to record who the two players even are — hence the two new columns, which also happen to distinguish paired `matches` from the legacy single-player ones for free (just filter `player_a_id is not null`, no need to infer it from a `match_results` count). `lib/actions/matches.ts` (`createPairedMatch`/`recordPairedResult`/`updatePairedResult`/`removePairedMatch`) and `app/admin/(shell)/[accountId]/partidas/partidas-section.tsx` implement this, parameterized by `sourceType: 'live'|'caxetao'` — but **only the Caxetão page (`/admin/[accountId]/partidas/caxetao/[eventId]`) still uses this path** today; the live-session version was superseded by the global cross-account flow below. It's reached from a "Partidas" button on the Caxetão event page itself (`app/admin/(shell)/[accountId]/caxetao/[eventId]/page.tsx`) once registrations are closed — the old `/admin/[accountId]/partidas` index that used to link into it was deleted (see next section).

## Partidas is a global area now — Nova Partida / Jogar (implemented)

Partidas stopped being nested under an account (`/admin/[accountId]/partidas/...`, with "my account" always fixed as one side of a confronto) and became its own top-level sidenav group — `app/admin/(shell)/layout.tsx`'s "Partidas" `nav-group`, split into two routes/labels: **Nova Partida** (`/admin/partidas/criar`) and **Jogar** (`/admin/partidas/jogar`). `app/admin/(shell)/account-sidenav-links.tsx` (the client component that used to also carry the "Partidas" link, reading `accountId` from the URL) now only carries "Pontuação".

Confrontos between two different accounts still live in the separate `cross_account_matches` table (`20260724000025_cross_account_matches.sql`, not `matches` — see the "no ranking leak" reasoning two sections down). What changed is how the two sides get picked and who can create one:

- **`/admin/partidas/criar`** (`page.tsx` + `criar-partida-section.tsx`): a symmetric two-column picker, labeled **Jogador 1** / **Jogador 2** (not "Lado A/B", not "Streamer" — picks `tiktok_accounts` directly, since an account is unambiguous even for a streamer who owns more than one; picking by streamer name first was dropped). Selecting an account auto-selects its open live when there's exactly one (the normal case — a manual live picker only appears as a fallback if an account somehow has more than one open live). Neither side is "me": the account list has no exclusion, since a moderador with no account of their own might be setting this up between two other streamers.
  - `createCrossAccountMatch` (`lib/actions/cross-account-matches.ts`) can't know upfront which of the two picked accounts the caller actually has `admin_account_access` to (the INSERT policy, `cross_account_matches_insert_creator_side`, only allows `has_account_access(account_id)`) — it tries the insert with Side A (Jogador 1's account) as `account_id` first, and on rejection retries with the sides swapped. If neither works, the caller has access to neither side and shouldn't be creating this partida. Verified with a throwaway script covering both the swap-succeeds and neither-side-accessible-rejects cases.
  - Once both sides have a live selected, a **Confrontos** table appears under the button, listing every confronto already built between that exact pair of lives (matched in JS against *both* orderings of `live_session_id`/`opponent_live_session_id`, since the row may have landed either way round per the try/swap above). Columns: Jogador 1 / Jogador 2 / Opções. Each player cell has a 🔄 icon that opens a `Modal` listing that side's live participants — clicking one submits the swap immediately via `swapCrossAccountMatchPlayer` (no separate confirm step, unlike the Pontos flow below). Opções has a ✕ delete button (`removeCrossAccountMatch`, a real delete with a `confirm()` — the intent is the same 2 players can be paired again from scratch, not a soft-delete).
- **`/admin/partidas/jogar`** (`page.tsx`): lists the 10 most-recently-active "desafios" (see below) **the current admin has any access to** — no manual account filter needed, `cross_account_matches_select_either_side` RLS already scopes the `select` to rows where the caller has `has_account_access` on either side. Verified a third admin with access to neither account sees zero rows.

All four mutating actions in `lib/actions/cross-account-matches.ts` (`createCrossAccountMatch`, `setCrossAccountMatchWinner`, `setCrossAccountMatchPoints`, `swapCrossAccountMatchPlayer`, `removeCrossAccountMatch`) revalidate `/admin/partidas/criar`, `/admin/partidas/jogar`, and the specific desafio detail path — none of them take an `accountId` anymore (it was only ever used to build the old nested revalidatePath, never to query or authorize anything).

`notifyStreamer` (`lib/actions/notifications.ts`, "Iniciar partida") lost its only caller when the old account-nested `cross-streamer-section.tsx` was deleted — the action still works, just has no UI hookup until it's clear where "notify a streamer" belongs in the new Criar/Jogar split.

## "Desafio dos Influencers": grouping confrontos + launching points (implemented)

There's no explicit "partida" entity/table — a **desafio** is just every `cross_account_matches` row that shares the same `(live_session_id, opponent_live_session_id)` pair, grouped in JS (both on the `/admin/partidas/jogar` index and inline under `/admin/partidas/criar`, independently). The detail page, `app/admin/(shell)/partidas/jogar/[sessionId]/[opponentLiveSessionId]/page.tsx` (+ `desafio-section.tsx`), needs no `accountId` — both sides' `@handle` are read straight off `live_sessions.tiktok_accounts` for whichever live_session_id/opponent_live_session_id the URL names.

It's the "tela de execução" deferred when cross-streamer confrontos first shipped: a side box titled "Desafio dos Influencers" (date, `@handleA` vs `@handleB`, and a **win tally** — 1 per confronto won, not the sum of any points, confirmed against the user's own worked example), plus the confrontos table. Jogador 1/2 are read-only here (swapping a player only happens on `/admin/partidas/criar`, see above); Resultado reuses `setCrossAccountMatchWinner` unchanged. Pontos: `cross_account_matches` has `scoring_rule_id`/`points_awarded` (`20260724000027_cross_account_matches_points.sql`, no cascade on `scoring_rule_id`, `points_awarded` a snapshot — same reasoning as `match_results`). The `<select>` lists the **winning side's own** `scoring_rules` (resolved via `match.winner`, disabled until a winner is set) and is deliberately kept `value`-controlled by the *persisted* `scoring_rule_id`, not local state — picking a new option opens a confirm `Modal` ("Deseja salvar esse resultado?") without changing what's displayed; OK calls `setCrossAccountMatchPoints`, Cancelar just closes the modal and the select silently snaps back to the persisted value — no client-side revert logic needed.

Same isolation as always: none of this is ever read by `getRanking`/`getPeriodRanking` — `cross_account_matches` stays structurally separate from `matches`/`match_results`, so launching real points here still can't leak into any account's ranking. **Gotcha already fixed for this**: `getRanking`'s lifetime fallback (`lib/scoring/get-ranking.ts`, used when an account has no open `score_period`) gained `.not("matches.live_session_id", "is", null)` back when cross-streamer confrontos first shipped, so this table (and Caxetão) can never leak into the public ranking either.

## Notifications between admins (implemented)

Table `notifications` (`20260724000026_notifications.sql`) — plain message, no link yet, scoped per `admins` row (not shared with the recipient's moderadores). `notifyStreamer` (`lib/actions/notifications.ts`) validates the recipient is actually an approved streamer before inserting — see the note above about it currently having no caller in the UI.

The global masthead (`app/layout.tsx`, renders on every page, public and admin) became `async` and fetches the session — logged out still shows the "Área Restrita" link; logged in shows `NotificationBell` (`components/notification-bell.tsx`, bell with an unread badge, opens the shared `Modal` and marks everything read on open — no realtime/polling, the badge only reflects what was rendered on the last request, same "no Supabase Realtime in the MVP" stance already taken elsewhere) and `AccountMenu` (`components/account-menu.tsx`, a custom dropdown — no Radix installed in this project — with "Painel admin" and "Sair"). That "Sair" calls `signOutToHome` (new, `lib/actions/auth.ts`), which redirects to `/` — different from the existing `signOut` used inside the admin shell (`app/admin/(shell)/layout.tsx`), which still goes to `/admin/login`, because the masthead also renders on public pages where forcing a detour through the login screen would be wrong.

## `scoring_rules` is global, not per-account (implemented)

Used to be one set of 4 rules per `tiktok_account_id` (seeded by `create_tiktok_account`). The user wants a single platform-wide list instead. `20260725000028_scoring_rules_global.sql` deduped the 2 accounts' × 4 identical rows down to one canonical set (checked first: zero `match_results`/`cross_account_matches` referenced any of them yet, so no FK risk) and dropped the `tiktok_account_id` column entirely. Write access changed shape too — `scoring_rules_write_admin` (`has_account_access`) is gone, replaced by `scoring_rules_write_super_admin` (`is_super_admin()` only); read stays public. `create_tiktok_account` no longer seeds anything on account creation, since there's no more per-account copy to seed.

Every reader dropped its `.eq("tiktok_account_id", accountId)` filter (lives' results dropdown, Caxetão's `PartidasSection`, the Desafio detail page) and just reads the global list. The Desafio page (`.../desafios/[opponentLiveSessionId]/page.tsx`) used to fetch `myRules`/`opponentRules` separately since a confronto's winner could be on either account — now it's one `scoringRules` query shared by both sides, and `desafio-section.tsx`/`setCrossAccountMatchPoints` (`lib/actions/cross-account-matches.ts`) dropped the "does this rule belong to the winning account" check along with it. `/admin/[accountId]/pontuacao` still lives under an account URL (unchanged) even though its data isn't account-scoped anymore — the page now checks the caller's own `admins.is_super_admin` and hides `CreateRuleForm`/`RuleCard`'s Editar/Desativar/Excluir controls for anyone who isn't.

`tests/rls.test.ts`'s `describe("scoring_rules", ...)` block used to test cross-tenant isolation (owner A can't touch account B's rule) — rewritten to test the new model instead (no regular admin, owner or moderator, can write; anon can still read). It does **not** cover the "a super admin CAN write" positive control — would need a dedicated super-admin fixture in the suite's `beforeAll`, deliberately left as a known gap and verified instead with a throwaway script when this policy shipped, same as every other feature in this codebase. `scripts/smoke-test.ts` step 1 no longer expects a seed — it just reads whatever global rules already exist.

## Theme (dark/light)

Originally single-dark-theme by design; `components/theme-toggle.tsx` now flips a `data-theme` attribute on `<html>` between `dark` (default) and `light`, persisted to `localStorage`. Every component reads color through the `app/globals.css` custom properties (`--surface`, `--ink`, `--stroke`, etc.), which `@theme inline` maps straight through to Tailwind utilities (`bg-surface`, `text-ink`, ...) — so `:root[data-theme="light"]` overriding those same custom properties reskins the whole site without touching component code, no `dark:`/`light:` utility variants needed anywhere. The exceptions are called out right next to the token declarations in `globals.css`: `--ink-on-accent` (fixed dark, for text on bright accent backgrounds like `.btn-yellow` that don't themselves flip with the theme) and the `--{red,yellow,green,purple}-text` tokens (badge/error text needs a darker tint on a light background to stay readable — the base accent colors are tuned for popping against dark mode's near-black tinted badges). `app/layout.tsx` runs a `beforeInteractive` inline script to set `data-theme` from `localStorage` before first paint — skipping it would flash the default dark theme for anyone who'd picked light. The toggle button itself lives in its own strip above every page's content (not a floating overlay) specifically to avoid colliding with each page's own top-right content (status badges, nav links, ...) — that was tried first and had to be reverted after overlap on more than one page.
