## What this project is

A platform to manage a TikTok creator's live "Cacheta" (card game) streams: manual scoring of matches per live session, weekly/season rankings, a Saturday "Cachetão" event with configurable registration (principal/substitute slots, closing by time or by count), World-Cup-style championships (groups → knockout), and multi-account management (one platform, several managed TikTok accounts, admins/moderators scoped per account).

Full domain rules, entities, and the proposed Postgres schema are in `prd.md` §4–§7 — do not re-derive these from scratch, reference them.

## Key architectural constraints (non-obvious, drives everything)

- **No TikTok API access for live/follower data.** There is no official API to read live-room participants or a creator's follower list. All match results are entered manually by an admin/moderator through the panel during/after the live. "Active/most engaged followers" are computed from in-platform activity (matches played, live participations, Cachetão/championship participation) — never fetched from TikTok. See `prd.md` §1.1.
- **Players are global, participation is per-account.** A `players` row is one person across the whole platform; their scores, live participations, Cachetão registrations, and championship history are always scoped to a `tiktok_account_id`. Any query/feature touching scores or rankings must filter by the active managed account.
- **Players have no password-based auth** (lightweight signup: display name + unique TikTok handle, optional WhatsApp). Only admins/moderators authenticate (Supabase Auth). Don't build a full auth flow for players in the MVP.
- **Scoring rules are per-account and admin-configurable**, not hardcoded constants — points for each result type (e.g. "vitória lambreta", "derrota normal") live in a `scoring_rules` table and are editable without a code change. `match_results.points_awarded` is a snapshot at write time, so historical totals must never be recalculated from current `scoring_rules` values.
- **Multi-tenancy by TikTok account**: an admin can own/moderate several `tiktok_accounts`; access is governed by `admin_account_access` (role: owner/moderator per account). Authorization (Supabase RLS) should key off this join table, not off a single global admin role.

## Fase 1 (MVP) — implemented

Migrations `supabase/migrations/2026071500000{1..11}_*.sql` create `admins` (1:1 with `auth.users`), `tiktok_accounts`, `admin_account_access`, `players`, `scoring_rules`, `score_periods`, `live_sessions`, `live_participants`, `matches` (with `tiktok_account_id` denormalized — deliberate deviation from prd.md §7 to keep every write policy a single `has_account_access()` check instead of a join), and `match_results`. Two SECURITY DEFINER helper functions (`has_account_access`, `is_account_owner`) back nearly every RLS policy — reuse them rather than re-writing the `admin_account_access` exists-subquery. Accounts are created exclusively through the `create_tiktok_account` RPC (also seeds the 4 default `scoring_rules`), because `tiktok_accounts` has no direct insert policy — the first `admin_account_access` row for a new account can't otherwise satisfy `is_account_owner()`.

Later migrations (`2026071700001{3,4}_*.sql`): `score_periods` gained an open/closed `status` (unique partial index caps it at one open period per account) and `live_sessions`/`matches` gained a denormalized `score_period_id`, copied from the live session onto every match via a `BEFORE INSERT` trigger — mirrors the `tiktok_account_id` denormalization so a period's ranking is a single-level join (`lib/scoring/get-ranking.ts` → `getPeriodRanking`). **Gotcha this created and fixed**: any table that denormalizes `tiktok_account_id` (or similar) purely for RLS speed is a spoofing risk — `has_account_access(tiktok_account_id)` only validates the column value on the row being written, not that it actually agrees with a related row's real account (e.g. `matches.live_session_id` could point at a different account's live session while `tiktok_account_id` still names an account the caller owns). `matches` now has a second trigger (`matches_validate_account`) that raises if the two disagree — replicate that pattern for any future denormalized-account-id table instead of trusting RLS alone. Admin UI for all this lives at `/admin/[accountId]/ranking` (current period + podium + close action) and `/admin/[accountId]/ranking/[periodId]` (historical periods); periods are created manually by the admin (label typed by them), never auto-opened.

`players` has no insert/update policy for anon or authenticated at all — both public self-registration and admin "quick add" during a live go through Server Actions using `lib/supabase/service.ts` (service-role, bypasses RLS), so handle normalization/dedupe lives in one place. Every other admin-facing write goes through the regular per-request client (`lib/supabase/server.ts`) and relies on RLS, not application-level role checks.

Admin routes live under `app/admin/(shell)/` (route group, doesn't affect the URL) so `app/admin/login` can render without the sidenav shell that the rest of `/admin/**` gets from `app/admin/(shell)/layout.tsx`. `proxy.ts` redirects unauthenticated requests to `/admin/login` for anything under `/admin` except that route.

Self-signup (the "Criar conta" mode on the login form) used to grant full admin capability the moment the email was confirmed — any visitor could sign up and immediately call `create_tiktok_account()`. Migration `20260718000018_admins_approval.sql` adds `admins.status` (`pending` by default for new signups, existing rows backfilled `approved`); `lib/supabase/middleware.ts` (`proxy.ts`) redirects any authenticated-but-not-approved admin to `/admin/aguardando` for everything under `/admin` except that page and `/admin/login`, and `create_tiktok_account` itself re-checks `is_approved_admin()` as defense in depth (same reasoning as `matches_validate_account` — don't trust a single layer). An existing approved admin reviews the queue at `/admin/solicitacoes` (`lib/actions/admin-approvals.ts`): "Aprovar" is a plain RLS-gated update (`admins_approve_pending` policy, pending → approved only) on the regular per-request client; "Excluir" needs the service-role client instead, since deleting the underlying `auth.users` row (which cascades to `admins`) isn't something any RLS policy can grant — the caller's own approved status is checked explicitly there for the same reason `adminRegisterPlayer` checks it (service role bypasses RLS entirely). **Gotcha this created and fixed**: an UPDATE policy's `with check` isn't the only thing that can reject a status-changing write — Postgres also re-validates the *mutated* row against the table's SELECT policies whenever the caller might get that row back (which PostgREST's `.update()` does even without an explicit `.select()`), and fails with the exact same "new row violates row-level security policy" error either way. A SELECT policy scoped to `status = 'pending'` let the approve `UPDATE` find the row but then couldn't see it anymore once its status flipped to `'approved'`; the fix was broadening `admins_select_all_for_approved` to cover every row, not just pending ones. `tests/rls.test.ts` and `scripts/smoke-test.ts` both fast-forward their throwaway admins to `'approved'` right after creating them — they test tenant isolation, not this gate.

`lib/scoring/get-ranking.ts` is the single source of truth for ranking math (points desc → count of positive-point results desc → handle alphabetical). The exact "vitórias lambreta"-specific tie-break from prd.md §12 is still an open decision (scoring_rules has no category column to distinguish a lambreta win from a normal one) — don't invent a category column without checking that decision first.

## Fase 2 (Cachetão) — implemented

Migrations `supabase/migrations/2026071700001{5,6,7}_*.sql` add `cachetao_events` and `cachetao_registrations`, then extend `matches` with a `cachetao_event_id` column so a match can belong to either a live session or a Cachetão event (`matches_exactly_one_source` check constraint), extending `matches_validate_account`/`matches_set_score_period` accordingly — Cachetão matches deliberately get no `score_period_id`, since Cachetão is a separate competition from the weekly/season ranking. `cachetao_registrations` has no insert policy for anon/authenticated at all (same reasoning as `players`): both self-registration and admin manual add funnel through `registerPlayerForEvent` (`lib/cachetao.ts`) on the service-role client, which is the one place that assigns principal-vs-substitute and FIFO `queue_position`. Status *updates* after creation (presence, cancellation, promotion) go through the regular per-request client instead, since admin already has direct RLS write access there and there's no cross-row math to protect.

`lib/cachetao.ts` also has `syncCachetaoEventStatus` — lazily flips `scheduled → registrations_open → registrations_closed` against the wall clock (same "no cron in this stack" pattern as `closeStaleLiveSessions`), called wherever a single event is read before acting on it. **Gotcha this created and fixed**: `registerPlayerForEvent` originally closed the event (`status = 'registrations_closed'`) as soon as `max_principals` was reached — but prd.md §4.5 says players beyond that cap should keep signing up as substitutes (up to `max_substitutes`), so reaching the principal cap must *not* stop registration outright. It now only auto-closes once principals **and** substitutes are both at capacity; an event with an uncapped substitute queue (`max_substitutes` null) is therefore never auto-closed by count, only by the time deadline or an admin. The three pt-BR label maps (`CACHETAO_STATUS_LABEL`, `CACHETAO_STATUS_VARIANT`, `CACHETAO_CLOSE_RULE_LABEL`) live in this same file — every page that renders an event's status/close_rule imports them rather than redefining its own copy.

The admin "Novo Cachetão" form (`create-event-form.tsx`) only offers `close_rule` **time** or **count** as a two-button toggle (no default selected, submit disabled until one is picked) — `both` is still a valid DB value and still handled by `createCachetaoEvent`/`registerPlayerForEvent`, it's just not reachable from this form; a deliberate scope-simplification, not a bug, if you're wondering why the UI only shows two options where the schema allows three. The two field groups (time window vs. capacity) are mutually exclusive and always render on their own row, never mixed with `Data do evento`/`Regra de encerramento`. Picking "Por quantidade" submits `registration_opens_at` as "now" (São Paulo wall time, via `nowInSaoPauloAsDatetimeLocal`) through a hidden input instead of asking the admin to schedule an opening — that mode has no deadline for an opening time to be scheduled against.

Admin UI lives at `/admin/[accountId]/cachetao` (list + create) and `/admin/[accountId]/cachetao/[eventId]` (principals/substitutes, manual add via modal, cancel/no-show, FIFO promotion, `Iniciar evento`/`Finalizar evento` stage transitions). Both the list and detail cards follow a title/subtitle/plain-text hierarchy: `Data · Regra` in `font-display` as the title, rule-specific values as an `.text-ink-dim` subtitle, and — only while registration is open — a third plain-text line with either a live countdown (`components/closing-countdown.tsx`, `ClosingCountdown`) or "Faltam N jogadores para encerrar as inscrições".

**Player view (public, no auth)**: `app/(public)/[accountHandle]/layout.tsx` wraps `ranking`/`cachetao`/`inscricao` in a shared tab nav (`components/ui/tab-bar.tsx` — also used by the admin account shell, see below). `/[accountHandle]/cachetao` shows the same principals/substitutes lists as admin, a `.card-stat`-styled (big number) countdown-or-remaining-slots readout for extra visibility, and self-registration via a modal (`cachetao-register-modal.tsx`) instead of an inline form. `RankingBoard` (`components/ranking-board.tsx`, shared by admin and public ranking pages) got a search box that filters by name/@handle while still showing each match's real rank, not its index in the filtered list. The root `/` page is the player entry point — it lists active `tiktok_accounts` linking into their `/ranking`, with `/admin/login` demoted to a small link at the bottom instead of being the page's main call to action.

`components/ui/modal.tsx` is a `<dialog>`-backed modal shared by every "open a form in a modal" flow (`register-player-modal.tsx`, `cachetao-register-modal.tsx`) — it renders the `<dialog>` itself as an invisible full-viewport flex-centering frame with the visible card as a nested `.modal-content` div. **Gotcha this created and fixed**: don't center a `<dialog>` by relying on the UA stylesheet's `dialog:modal { margin: auto }` — Tailwind v4's Preflight resets `margin: 0` in `@layer base`, and even though that's a *lower*-priority layer than unlayered author CSS, it's still higher priority than the UA stylesheet's own (lowest) tier, so Preflight's reset silently wins and the dialog collapses to the top-left corner. Center with flex (`.modal-overlay[open]{ display:flex; align-items:center; justify-content:center; }`) instead — it has no dependency on margin at all. `ModalHeader` (title + close-✕ button) is exported from the same file since it was identical boilerplate at every modal call site.

**Known gap**: `tests/rls.test.ts` does not yet cover `cachetao_events`/`cachetao_registrations` — deferred to the end of the phase per explicit instruction rather than extended after each migration (unlike the stated convention above). Extend it before starting Fase 3.

## Super admin & account deletion (implemented)

Migration `20260724000020_super_admin.sql` adds `admins.is_super_admin` (boolean, default false) and redefines `has_account_access`/`is_account_owner` (`20260715000003_admin_account_access.sql`) to `... or is_super_admin()` — gives a super admin automatic access to every one of the ~14 tables those two functions already gate. This is a deliberate override of this file's own earlier note ("authorization should key off `admin_account_access`, not a single global admin role") — the user explicitly asked for someone who can manage every account and every admin at once. `revoke update (is_super_admin) on admins from authenticated, anon` stops an already-approved admin from self-escalating via `.update({status:'approved', is_super_admin:true})` through `admins_approve_pending`'s loose `with check` (which only pinned `status`) — RLS row policies can't express "this column is off-limits regardless of the row predicate," only a column-level revoke does. The first super admin was seeded directly: `update admins set is_super_admin = true where email = 'nelsonhaproenca@gmail.com'`.

Account deletion (`delete_tiktok_account` RPC, `20260724000021`) mirrors `create_tiktok_account`: `tiktok_accounts` has no direct delete policy, only this `security definer` RPC, gated by `is_account_owner` and requiring the caller to re-type the account's `@handle` as confirmation (`app/admin/(shell)/contas/delete-account-modal.tsx`) — given the blast radius (wipes the account's entire ranking, lives, results, and Cachetão history). **Gotcha fixed in `20260724000022`**: `match_results.scoring_rule_id` and `match_result_edits.*_scoring_rule_id` have no `on delete cascade` to `scoring_rules` (by design — see `20260715000011_match_results.sql`), so the cascade from `tiktok_accounts` reached `scoring_rules` before those two tables were empty and the FK check fired mid-cascade. The RPC now deletes `match_result_edits`/`match_results` scoped to the account explicitly before the delete that cascades through the rest — same fix already used in `scripts/smoke-test.ts`'s `cleanup()`.

## User roles: Streamer, Moderador, Super Admin (implemented)

Migration `20260724000024_admin_user_type.sql` adds `admins.user_type` (`'streamer'|'moderador'`, nullable — a super admin doesn't need one) and `admins.streamer_id` (self-FK, `on delete set null`, only set for moderadores). **This is orthogonal to `admin_account_access.role`** (`'owner'|'moderator'`, English, per-account — untouched) — the two similar-looking values (`moderator` vs `moderador`) name different things on purpose: one is an access level on one account, the other is the category of person. A streamer can still own several accounts (this did not become a 1:1 relationship). Signup (`app/admin/login/login-form.tsx`, "Criar conta" mode) now picks the type and, for moderadores, which streamer to link to — the streamer list comes from `app/admin/login/page.tsx` via `createServiceClient()`, since that page renders pre-session and `admins` has no public select policy. Trigger `admins_validate_streamer` rejects a `streamer_id` that doesn't point at a real `user_type='streamer'` row.

Approving an admin now goes through the RPC `approve_pending_admin` instead of the old direct `update({status:'approved'})` — the `admins_approve_pending` policy was **removed**, this RPC is the only path now (same "no direct write policy, only via RPC" pattern as `create_tiktok_account`). Approving a moderador auto-copies the same `admin_account_access` rows (`role='moderator'`) their linked streamer already has — that's how "same access as the streamer" is satisfied without waiting on a manual `AddModeratorForm` afterward. It's only a snapshot at approval time though: if the streamer gains a new account later, the moderador isn't synced automatically — that still needs the existing manual flow (`lib/actions/accounts.ts`'s `addModerator`) for that specific account.

## Partidas: pairing 2 players within one account (implemented)

`matches` gained `player_a_id`/`player_b_id` (nullable, `20260724000023_matches_player_pairing.sql`) to hold a real 2-player pairing on a single `matches` row — until then every `matches` row was created with **one** player only (`recordMatchResult`, `lib/actions/lives.ts`), never two. `match_results` is untouched (still `not null`), so a freshly-created pairing with no result yet needs somewhere to record who the two players even are — hence the two new columns, which also happen to distinguish paired `matches` from the legacy single-player ones for free (just filter `player_a_id is not null`, no need to infer it from a `match_results` count). `lib/actions/matches.ts` (`createPairedMatch`/`recordPairedResult`/`updatePairedResult`/`removePairedMatch`) and `app/admin/(shell)/[accountId]/partidas/partidas-section.tsx` implement this, parameterized by `sourceType: 'live'|'cachetao'` — but **only the Cachetão page (`/admin/[accountId]/partidas/cachetao/[eventId]`) still uses this path** today; the live-session version was superseded by the global cross-account flow below. It's reached from a "Partidas" button on the Cachetão event page itself (`app/admin/(shell)/[accountId]/cachetao/[eventId]/page.tsx`) once registrations are closed — the old `/admin/[accountId]/partidas` index that used to link into it was deleted (see next section).

## Partidas is a global area now — Nova Partida / Jogar (implemented)

Partidas stopped being nested under an account (`/admin/[accountId]/partidas/...`, with "my account" always fixed as one side of a confronto) and became its own top-level sidenav group — `app/admin/(shell)/layout.tsx`'s "Partidas" `nav-group`, split into two routes/labels: **Nova Partida** (`/admin/partidas/criar`) and **Jogar** (`/admin/partidas/jogar`). `app/admin/(shell)/account-sidenav-links.tsx` (the client component that used to also carry the "Partidas" link, reading `accountId` from the URL) now only carries "Pontuação".

Confrontos between two different accounts still live in the separate `cross_account_matches` table (`20260724000025_cross_account_matches.sql`, not `matches` — see the "no ranking leak" reasoning two sections down). What changed is how the two sides get picked and who can create one:

- **`/admin/partidas/criar`** (`page.tsx` + `criar-partida-section.tsx`): a symmetric two-column picker, labeled **Jogador 1** / **Jogador 2** (not "Lado A/B", not "Streamer" — picks `tiktok_accounts` directly, since an account is unambiguous even for a streamer who owns more than one; picking by streamer name first was dropped). Selecting an account auto-selects its open live when there's exactly one (the normal case — a manual live picker only appears as a fallback if an account somehow has more than one open live). Neither side is "me": the account list has no exclusion, since a moderador with no account of their own might be setting this up between two other streamers. A client-side check blocks submitting with the same account on both sides (`alert-error`, "As duas contas são a mesma...") before the form is even enabled — `createCrossAccountMatch` re-checks the same thing server-side.
  - Once both sides have a live selected, a **Confrontos** table appears under the button, listing every confronto already built between that exact pair of lives (matched in JS against *both* orderings of `live_session_id`/`opponent_live_session_id`, since a partida's `account_a`/`account_b` may land either way round — see below). Columns: Jogador 1 / Jogador 2 / Opções. Each player cell has a 🔄 icon that opens a `Modal` listing that side's live participants — clicking one submits the swap immediately via `swapCrossAccountMatchPlayer` (no separate confirm step, unlike the Pontos flow below). Opções has a ✕ delete button (`removeCrossAccountMatch`, a real delete with a `confirm()` — the intent is the same 2 players can be paired again from scratch, not a soft-delete).
- **`/admin/partidas/jogar`** (`page.tsx`): lists every partida (see below), newest first, **the current admin has any access to** — no manual account filter needed, `partidas_select_either_side` RLS already scopes the `select` to rows where the caller has `has_account_access` on either side. ## `partidas`: a real record instead of an implicit grouping (implemented)

`20260727000030_partidas.sql` adds a `partidas` table — `id`, `name`, `account_a_id`/`account_b_id`, `live_session_id`/`opponent_live_session_id`, `created_by`, `created_at` — and `cross_account_matches.partida_id` (not null) pointing at it. Before this, a "partida" (what the UI already called a **desafio**) was purely an implicit grouping: every `cross_account_matches` row sharing the same live-session pair, recomputed in JS on every page load. That worked for display but couldn't hold a name, and had no way to lock the two sides once set. Backfilled from existing data (grouped by live-session pair, named the same way new ones are, oldest confronto's `created_at` as the partida's) before `partida_id` was made `not null` — verified against the 5 real rows/2 pairs that existed at migration time.

- **Name**: `buildPartidaName` (`lib/utils.ts`) — `@handleA_X_@handleB_yyyymmdd_hhmm` in São Paulo time (same fixed UTC-3 assumption as the rest of that file), generated once when a partida is first created and never touched again.
- **Immutability**: `partidas` has **no update policy at all** — not "locked by convention in the UI," genuinely impossible to change `account_a_id`/`account_b_id`/the two live session ids through the API once inserted. `partidas_check_accounts` (trigger, mirrors `cross_account_matches_validate`) still validates on insert that `account_a_id`/`account_b_id` actually match their live session's real account — same denormalization-spoofing defense as everywhere else. A `check` constraint (`partidas_distinct_accounts`) also rejects `account_a_id = account_b_id` at the DB level, not just the client-side warning on `/admin/partidas/criar`.
- **Creation/reuse** (`resolvePartida`, `lib/actions/cross-account-matches.ts`): before inserting a confronto, looks for an existing partida covering this exact live-session pair (`.or()` matching both orderings — a partida's `account_a`/`live_session_id` reflects whichever side the RLS insert-creator-side check let through, same as the old per-confronto try/swap). If none exists, tries inserting with Side A as `account_a_id` first, retries swapped on RLS rejection (`partidas_insert_creator_side` only allows `has_account_access(account_a_id)`) — same two-attempt dance `cross_account_matches` already used, just one level up. The confronto insert right after reuses whichever orientation won, so it only needs its own try/swap when *reusing* an existing partida created by a different admin who has access to the other side. Verified with a throwaway script: swap-fallback creation, same-pair reuse (no duplicate partida, both confrontos share one `partida_id`), the DB check constraint, and RLS denial for an admin with access to neither side.
- **Editing** (`/admin/partidas/criar/[partidaId]`, `app/admin/(shell)/partidas/criar/[partidaId]/page.tsx`): reached via an "Editar" button on each `/admin/partidas/jogar` row. Reuses `CriarPartidaSection` with a `lockedPartida` prop instead of a second component — `SidePicker` renders the account as plain text (no `<Select>` at all) when locked, so the two sides genuinely can't be changed from this screen either, only the player picker and the confrontos table (add/swap/remove) stay interactive. `live_participants` for both sides are queried fresh on every visit to this page (a plain server-component fetch, no caching to invalidate) so players who joined a live after the partida was first created still show up as pickable.
  - **Read-only once either live ends**: the edit page calls `closeStaleLiveSessions` for both accounts (same lazy auto-close as `/admin/[accountId]/lives`) then checks both `live_sessions.status`. If either side is `closed`, `CriarPartidaSection` takes an early-return branch (still after all its hooks, not before — a conditional-hooks bug caught during review) that renders only the confrontos list (Jogador 1/Jogador 2 as plain text, no 🔄 swap, no ✕ remove, no add-confronto form) — there's no participant pool left to pick from once a live has ended, so add/swap/remove would have nothing to offer anyway. Both lives still open renders the normal interactive screen.
- **"Jogar" also gated on both lives being open**: `/admin/partidas/jogar`'s list computes the same `bothLivesOpen` check (via a batched `live_sessions` status query + `closeStaleLiveSessions` per involved account) and only renders the "Jogar" button when true — otherwise a plain "Live encerrada" label takes its place, no link. The "Jogar" `<Link>` needed `btn-primary` added explicitly alongside `btn-sm`: unlike the `Button` component (`components/ui/button.tsx`), which defaults to the `primary` variant via `cva`'s `defaultVariants`, a raw `className="btn btn-sm"` string on a plain `<Link>` gets none of that — `.btn` alone has no background/color in `globals.css`, so the button rendered unstyled next to "Editar"'s `btn-outline`.

## Cachetão cross-account partidas — and the one deliberate ranking-isolation exception (implemented)

A global **Cachetão** sidenav group (`app/admin/(shell)/layout.tsx`, matching `/admin/cachetao`), same style as Partidas: **Criar** (`/admin/cachetao/criar` — creates a `cachetao_events` row, reusing the same `CreateEventForm` as `/admin/[accountId]/cachetao` but with an account `<select>` instead of an implicit accountId, via a discriminated-union prop) and **Jogar** (`/admin/cachetao/jogar` — pairs two players from two *different* accounts' Cachetão events against each other, mirroring the live-based Partidas flow but sourced from `cachetao_registrations` instead of `live_participants`).

`20260728000031_cachetao_cross_account_matches.sql` extends `partidas` and `cross_account_matches` with `cachetao_event_id`/`opponent_cachetao_event_id` (mirroring the live/cachetao dual-source pattern `matches` already used, `20260717000017`) — `live_session_id`/`opponent_live_session_id` on both tables became nullable, with a check constraint per side requiring exactly one of the two sources. `partidas_validate`/`cross_account_matches_validate` (triggers) were extended to validate `account_a_id`/`account_b_id` (or `account_id`/`opponent_account_id`) against whichever source is actually set. Every existing page that reads `partidas`/`cross_account_matches` unconditionally (the live-based Partidas screens, predating this) now explicitly filters `.not("live_session_id", "is", null)` — a `partidas`/`cross_account_matches` row can be either kind now, and those pages only ever know how to render the live-sourced one.

- **`lib/actions/cross-account-matches.ts`** gained a parallel `resolveCachetaoPartida`/`createCachetaoCrossAccountMatch` (kept as separate functions from the live-sourced `resolvePartida`/`createCrossAccountMatch` rather than parametrized — the two flows are reached from entirely different screens and never mix sources within one partida). Eligible players for each side are `cachetao_registrations` with `status in ('confirmed', 'called_up')` (excludes `cancelled`/`no_show`) — mirrors why the account-scoped Cachetão pairing button only appears once registrations are closed.
- **The four shared mutation actions** (`setCrossAccountMatchWinner`, `setCrossAccountMatchPoints`, `swapCrossAccountMatchPlayer`, `removeCrossAccountMatch`) needed no source-specific duplicates — they were refactored to read a confronto's own source columns and derive both pool-validation (live_participants vs cachetao_registrations) and revalidation paths (`revalidateConfrontoPaths`) from the row itself, rather than trusting `session_id`/`opponent_live_session_id` hidden inputs the caller used to have to supply. Those hidden inputs are simply ignored now if a caller still sends them (the existing live-based UI does, harmlessly) — this is why `criar-partida-section.tsx`/`desafio-section.tsx` needed zero changes despite the action signatures changing underneath them. `DesafioSection` (the Resultado/Pontos table) is reused as-is by the Cachetão desafio page (`sessionId`/`opponentLiveSessionId` props made optional, default `""`) — it never had any live-specific logic in it to begin with, just hidden inputs.
- **Ranking mirroring — the one deliberate exception to "cross_account_matches never touches ranking"**: everywhere else in this file, launching points on a confronto stays fully isolated from any account's ranking (see the "Same isolation as always" note above). This one case doesn't: closing this specific loop (Cachetão is a real competitive event, not a casual live-time challenge) was an explicit decision, confirmed against three specific questions before building it — (1) only *this* cross-account flow counts, the existing single-account Cachetão pairing (`/admin/[accountId]/partidas/cachetao/[eventId]`) stays excluded exactly as before; (2) only the **winner** scores (the loser gets nothing, unlike a normal match's two-sided `match_results`); (3) launching is **blocked** if the winner's account has no open `score_period`, never silently orphaned outside a period. `setCrossAccountMatchPoints` implements this only when the confronto is Cachetão-sourced: looks up the winner's account/event/player, requires an open `score_periods` row for that account (else returns an error), then upserts a `matches` row (via `createServiceClient()` — the admin acting on this confronto may only have `has_account_access` on the *losing* side, which is fine, since managing the confronto at all is itself the authorization for this side effect) with `cachetao_event_id` set and `score_period_id` set **explicitly** to the open period's id, plus a `match_results` row for the winner only.
  - **Why this doesn't need any changes to `getRanking`/`getPeriodRanking`**: `matches_set_score_period` (the trigger that normally fills `score_period_id`) only ever does so for live-sourced matches — for a cachetao-sourced insert it's a no-op, which means an explicitly-provided `score_period_id` in the INSERT payload survives untouched. `getPeriodRanking` filters purely on `matches.score_period_id`, with no live-vs-cachetao distinction at all — so a cachetao-sourced match with a real `score_period_id` shows up correctly with zero query changes. `getRanking`'s lifetime fallback (no open period) still excludes it via the pre-existing `.not("matches.live_session_id", "is", null)` filter, same as ever — but that fallback is only ever used when an account has *no* open period at all (confirmed by reading both ranking pages), which can't happen for a match that was only ever allowed to be created *because* an open period existed.
  - `matches.source_cross_account_match_id` (nullable, unique-when-set) marks a mirrored row — lets `setCrossAccountMatchPoints` upsert in place in place of re-inserting when points are relaunched with a different rule, and lets `setCrossAccountMatchWinner` delete the mirrored row whenever the winner actually changes (clearing the confronto's own `scoring_rule_id`/`points_awarded` at the same time) — otherwise a changed winner would leave stale ranking credit sitting on the wrong account with no way to reconcile it.
  - Verified end to end with a throwaway script: partida/confronto creation via the RLS-gated per-request client, blocked launch with no open period, successful launch with one (confirmed the trigger doesn't clobber the explicit `score_period_id`), `getPeriodRanking` reflecting the winner's points, mirrored-match cleanup on a simulated winner change, and a regression check that a plain within-account Cachetão match still doesn't leak into `getRanking`'s lifetime fallback.

No "pending/approval" concept for players — `link_or_create_player` resolves synchronously right after OTP verification. `app/layout.tsx`'s global masthead and `AccountMenu` now branch on `isAdmin` (checked via an `admins` row lookup) so a logged-in player sees "Minha conta" → `/minha-conta` instead of a "Painel admin" link that would just dead-end them at `/admin/aguardando`.

**Gotcha found and fixed twice this phase — column/function-level `revoke` is a no-op against this project's default privileges.** `players_select_public` (`using (true)`) predates `auth_phone`; a plain `revoke select (auth_phone) on players from anon, authenticated` (`20260801000035`) looked right but **did nothing** — verified directly against `information_schema.column_privileges`. Root cause: this project grants table-wide `SELECT`/`EXECUTE` to `anon`/`authenticated` **automatically at CREATE time** (a default-privileges rule, independent of the `PUBLIC` pseudo-role), and a column has no privilege check of its own until it has an *explicit* column-level grant — a `REVOKE` on a column that only ever inherited from the table-level grant has nothing to remove. Same bug bit the brand-new `list_live_broadcasts_now()`/`get_live_broadcast_public()` RPCs: `revoke all ... from public; grant ... to authenticated` still left `anon` able to call them (`information_schema.routine_privileges` confirmed it), because `anon` gets `EXECUTE` on new functions the same automatic way. **The fix, and the pattern to replicate for any future sensitive column/function**: for a column, `revoke select on table from anon, authenticated` (the *whole table*) then `grant select (explicit, column, list) on table to anon, authenticated` — enumerate every column except the sensitive one, don't try to subtract just the sensitive one. For a function, `revoke all ... from public, anon` explicitly (not just `public`) — and for functions that aren't already gated by their own `auth.uid()`/`current_player_id()` logic, add that check inside the function body too as defense in depth, since a future privilege change could silently reopen the same gap otherwise. `has_account_access`/`is_account_owner`/etc. (pre-existing, `20260715000003`) turned out to have the same `anon`-can-execute gap, confirmed harmless only because their bodies already null out on `auth.uid()` — not fixed (touching an old migration would misrepresent history), but worth knowing before assuming an old `revoke ... from public` actually restricts anything.

**M6 — in-app live streaming** (`20260801000037_live_broadcasts.sql` + `20260801000038` fixing the gotcha above). `live_broadcasts` is deliberately **linked** to the pre-existing `live_sessions` (the manual-scoring-during-a-live concept) rather than parallel — starting a transmission (`lib/actions/live-broadcasts.ts` → `startBroadcast`/`getOrCreateOpenLiveSession`) reuses the account's already-open `live_sessions` row if one exists, or opens one, so a streamer has one concept of "the live," not two. `live_broadcasts_validate_account` mirrors `matches_validate_account`'s denormalization-spoofing defense. `stream_key` (RTMP/WHIP publish secret) is never exposed by the base table — its `SELECT` RLS is admin-only (`has_account_access`) — and the two player-facing read paths are `security definer` RPCs (`list_live_broadcasts_now`, `get_live_broadcast_public`). `live_broadcasts` has **no UPDATE RLS policy at all** (not even a column-revoke, stricter than the `is_super_admin` pattern which turned out to be a no-op — see the gotcha above) — `status`/`started_at`/`ended_at`/`srs_stream_id` only ever change via the media-server callback routes (service-role, validate a shared secret) or `endBroadcastManually` (service-role, but only after an RLS-gated read confirms `has_account_access` first — same defense-in-depth shape as `admin-approvals.ts`'s "Excluir"). `components/broadcast/whip-publisher.tsx` (camera capture, admin) and `whep-player.tsx` (playback, player) are both hand-rolled `RTCPeerConnection` + single-shot SDP POST (no signaling channel, no new npm dependency, per explicit user decision), sharing `waitForIceGathering` from `components/broadcast/webrtc-utils.ts`; both also capture the WHIP/WHEP response's `Location` header and send a `DELETE` there on stop/unmount, so the media server frees the session immediately instead of waiting out an ICE/RTP timeout. Admin UI: new "Ao vivo" tab in the account shell (`TAB_SEGMENTS`) → `/admin/[accountId]/live` (list + "Ir ao vivo" button) → `/admin/[accountId]/live/[broadcastId]` (stream key/path, RTMP URL for OBS users, `WhipPublisher`, "Encerrar transmissão"). Player UI: `/ao-vivo` (list of everything currently `status='live'`, via the RPC) → `/ao-vivo/[broadcastId]` (`WhepPlayer` + chat). Both player routes require a linked player (M0's middleware guard) — **no anonymous vitrine**, confirmed decision.

**Corrected after M6 first shipped: the media server is MediaMTX, not SRS.** The original technical plan (and everything above when first written) assumed **SRS**. Inspecting the real VPS (over an already-open PuTTY session, pasted into the conversation) showed it's actually **MediaMTX** — and that instance is already in production serving an unrelated product of the user's, a camera-monitoring system ("Watchtower"), with `webrtcAddress: ""` (WebRTC/WHIP/WHEP off) and `paths` restricted to `~^camera_`/`~^bridge_` regexes. Nothing in the original design (query-string WHIP/WHEP URLs, an SRS-style `on_publish`/`on_unpublish` HTTP callback with an accept/reject response) matches MediaMTX's actual model, confirmed against `mediamtx.org/docs` rather than assumed:
- WHIP publish and WHEP read share the **same path-based URL** (`POST /<path>/whip`, `POST /<path>/whep`) on one `webrtcAddress` listener — there's no separate identifier for "watch" vs "publish" the way the original design used `broadcast.id` for playback and `stream_key` for publish, short of MediaMTX's Control API (not used, out of scope). **Revised, confirmed security model**: `get_live_broadcast_public` (`20260801000040`) now returns `playback_path` (`'live_' || stream_key`) but **only once `status = 'live'`** — a player who opens a broadcast's page before the real streamer has started gets nothing to act on, closing the window to squat on the path first. Once genuinely live, the real protection against a player trying to hijack it is MediaMTX only ever accepting **one publisher per path** — a second WHIP attempt against an already-live path is rejected by MediaMTX itself. `list_live_broadcasts_now()` still never includes this field at all — a player only ever learns a path by opening one specific broadcast's page, never the public listing.
- The correct config key is `webrtcLocalUDPAddress` (not `webrtcICEUDPMuxAddress`, wrongly assumed at first from SRS-shaped naming) and `webrtcAdditionalHosts` must list the VPS's public IP for ICE to work from outside.
- There's no `on_publish`/`on_unpublish` hook — the equivalent is **`runOnReady`/`runOnNotReady`** (a shell command MediaMTX runs, with `$MTX_PATH` available, not an HTTP POST with a JSON body) — hence `app/api/mediamtx/on-ready|on-not-ready/route.ts` (replacing the deleted `app/api/srs/on-publish|on-unpublish`) read `secret`/`path` from **query params**, not a request body, and have no "reject" response MediaMTX would honor (this is bookkeeping only — real access control is the path secrecy + single-publisher-per-path behavior above). **Second correction discovered applying this to the real VPS**: the docs fetched initially were for MediaMTX's `main` branch, which uses `runOnAvailable`/`runOnUnavailable` — the VPS is pinned to the older **v1.9.3**, which rejects those with `ERR: json: unknown field "runOnAvailable"` and use `runOnReady`/`runOnNotReady` instead (same semantics, older name); `webrtcAllowOrigin` is also singular/a plain string in v1.9.3, not the plural `webrtcAllowOrigins` list the `main` docs showed. Lesson: for a pinned-version service, verify config keys against that exact tagged version's sample config (`raw.githubusercontent.com/bluenviron/mediamtx/v<X.Y.Z>/mediamtx.yml`), not `main`.
- `authMethod`/`authHTTPAddress` are **global-only** in MediaMTX, not per-path — so the new `~^live_(.+)$` path is left with no `publishUser`/`publishPass`, same as the existing (commented-out) `camera_` path, rather than touching the shared `authMethod: internal` setting that the camera product depends on.
- `lib/srs.ts` was renamed to **`lib/mediamtx.ts`**; `buildWhipPublishUrl`/`buildWhepPlaybackUrl`/`buildRtmpPublishUrl` now take a full MediaMTX path (e.g. `` `live_${streamKey}` ``, built by the caller so the `live_` prefix isn't duplicated) instead of a bare key plus a `?app=&stream=` query string. Env vars renamed `SRS_RTMP_HOST`/`SRS_WHIP_PUBLISH_URL`/`SRS_WHEP_PLAYBACK_URL`/`SRS_CALLBACK_SECRET` → `MEDIAMTX_RTMP_HOST`/`MEDIAMTX_PUBLIC_URL`/`MEDIAMTX_CALLBACK_SECRET` (one URL now covers both WHIP and WHEP, since they share the host/port and differ only by path suffix).
- Because the VPS is shared with a paying production product, every VPS-side change (`mediamtx.yml`, nginx, ufw) is designed additive-only — a brand-new `~^live_(.+)$` path, a brand-new nginx site/subdomain (`live.<domain>`, proxying `127.0.0.1:8889` — MediaMTX's `webrtcAddress` is bound to localhost only, same pattern the file already uses for `hlsAddress`, with nginx as "the only public entry point," now extended to WebRTC too), a new UDP port for ICE — never touching the existing `camera_`/`bridge_` paths, the pre-existing `meu-projeto` nginx site (unrelated, confirmed with the user), or `authMethod`.

**M7 — live chat + moderation** (`20260801000039_live_chat.sql`, written with the M0/M6 gotcha already baked in — explicit `revoke ... from public, anon` plus an internal `auth.uid() is not null` check on the read side from the start). `live_chat_messages` has **no INSERT policy at all** — same "no direct write, only via RPC" shape as `players`/`cachetao_registrations` — `send_live_chat_message(broadcast_id, body)` (security definer) atomically resolves `current_player_id()`, checks the broadcast is actually `status = 'live'`, checks the player isn't in `live_chat_mutes` for that broadcast, validates a trimmed 1–300 char body, and inserts. The SELECT policy **deliberately does not filter out `deleted_at`** — Supabase Realtime's `postgres_changes` only delivers an `UPDATE` event to a subscriber whose SELECT policy still matches the row *after* the update, so hiding soft-deleted rows at the policy level would mean the delete-flip event silently stops being delivered to anyone already watching (their chat would show the message forever until a manual refresh); the client (`components/broadcast/live-chat.tsx`) filters `deleted_at` itself on both initial load and the realtime event instead. Moderation ("apagar mensagem" + "silenciar espectador," both in scope per explicit decision) is a plain RLS `UPDATE` policy (soft-delete, `has_account_access` via a join to `live_broadcasts`) for delete, and a `live_chat_mutes` table (insert/delete by the same join-based admin policy; a player can also `SELECT` their own mute row to disable their own input) for mute — no RPC needed for either, since there's no cross-row math to protect, same reasoning already used for Cachetão registration status updates. **Sending a message is a direct client-side `supabase.rpc()` call from the browser**, not a Server Action — first deliberate departure from this codebase's usual Server Action convention for a write, on the reasoning that a chat send shouldn't pay for a full form-action + `revalidatePath` round trip when the RPC already enforces every rule server-side regardless of caller; deleting/muting (admin-only, not latency-sensitive) stay as ordinary Server Actions (`lib/actions/live-chat.ts`). This is also the **first use of Supabase Realtime anywhere in this codebase** — `postgres_changes` (not Broadcast/Presence), which respects RLS natively via `alter publication supabase_realtime add table live_chat_messages`, deliberately chosen over Broadcast specifically so the "is Realtime Authorization enabled on this project" open question from `prd.md` §12 never needed answering.
